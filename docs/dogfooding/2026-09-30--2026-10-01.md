# AIES Dogfooding Synthesis: 2026-09-30 – 2026-10-01

This document provides a comprehensive, empirical synthesis of the two-day dogfooding sprint conducted on September 30 and October 1, 2026. Over this period, AIES was run as its own daily driver to identify, reproduce, and resolve critical workflow, isolation, runtime, and verification flaws.

The sprint processed 8 documented sessions totaling **564.4 minutes (~9.4 hours)** of execution and **117.2 million tokens**.

---

## 1. Evolution of the Daily-Driver Gate

The dogfooding strategy began by exercising AIES against external consumer repositories, specifically reproducing an acceptance criteria failure on `Mi-Porfolio/EZE-461`. However, once real bugfixes were attempted within AIES itself, the system encountered the "self-hosting gate": AIES trying to inspect, modify, and verify AIES.

This exposed foundational assumptions that held when operating on simple consumer repositories but failed when operating on a harness layer:
1. **Module Caching**: Consumer code changes are executed in fresh processes; AIES extensions are loaded in-process once at startup.
2. **Harness Isolation**: AIES unit tests test process bootstrap, launcher configuration, and filesystem permissions; executing those tests inside AIES's own read-only Verify sandbox caused recursive sandbox collisions (`listen EPERM`) and profile locks.
3. **Repository Identity**: Operating across multiple repositories (`AIES`, `Mi-Porfolio`) exposed the complete absence of repository identity checks in ticket handling, allowing Parent sessions to mutate whichever repository was in `cwd`.

The sprint shifted from external smoke testing to systematically hardening AIES so it could reliably verify and maintain itself without manual developer intervention.

## 2. Tickets and Issues Addressed

### EZE-487: Child Provider Label Disagreement
- **Problem**: When parent and child agents ran under different providers (e.g., Parent on `commandcode`, Child on `qwen-token-plan`), the UI right rail and `/agents` view displayed the parent's provider label or mixed them up.
- **Fix**: Commit [`e478f60`](https://github.com/EzequielMenor/AIES/commit/e478f60) ensured `providerId` and `providerLabel` move together via `providerDisplayLabel()`. The right rail was updated to project child metadata during active delegations.

### EZE-488: Structural Verify Acceptance Criteria Coverage
- **Problem**: In real runs on `Mi-Porfolio/EZE-461`, Verify completions were rejected by `validateVerifyCompletion` with `invalid_completion` protocol errors because criterion coverage relied on exact string equality. Minor LLM rewrites, typographical variations (em dashes, arrows, quotation styles), or whitespace resulted in rejected verdicts.
- **Fix**: Commit [`13f6567`](https://github.com/EzequielMenor/AIES/commit/13f6567) introduced a structural 1-based index contract (`VerifyCompleteSchema`) where criteria are indexed 1..N. The host injects the canonical criterion text upon acceptance. Added JSON array fan-out support in `normalizeCriteriaList`.

### EZE-490: Lossless Direct MCP Ticket Capture
- **Problem**: `aies_ticket` required the Parent LLM to manually copy the result of `mcp get_issue` into a `remote` parameter. The Parent LLM frequently summarized or truncated large issue descriptions, completely dropping `## Aceptación` sections and leaving tickets without explicit criteria.
- **Fix**: Commit [`84555fa`](https://github.com/EzequielMenor/AIES/commit/84555fa) added a direct `tool_result` event interceptor in `extensions/aies-agents/index.ts`. When `pi-mcp-adapter` delivers a `get_issue` payload, AIES captures it directly in code and hydrates `TicketManager.captureRemote`, eliminating LLM text re-serialization.

### EZE-489: Cross-Repository Ticket Mutation Guard
- **Problem**: Ticket contracts carried no repository or workspace identity. When a session started with `cwd` pointing to `Mi-Porfolio`, loading an AIES ticket allowed Parent to write and edit files in AIES, bypassing the Worker workspace boundary.
- **Fix**: Commit [`e4eea02`](https://github.com/EzequielMenor/AIES/commit/e4eea02) created `extensions/aies-agents/repo-guard.ts` (Decision D30). It matches ticket project metadata against repository identity derived from git root, blocking mutations, delegations, or destructive actions when mismatched.

### EZE-492: Fresh Runtime Requirement for Extensions (Stale Runtime Guard)
- **Problem**: Pi loads extensions once per process using `jiti`. Child sessions (Explore, Worker, Verify) are spawned in-process. When Parent or Worker modified `extensions/*.ts`, subsequent in-session Verify runs executed the stale in-memory modules while the filesystem had new code.
- **Fix**: Commit [`f374bfb`](https://github.com/EzequielMenor/AIES/commit/f374bfb) introduced `extensions/aies-agents/runtime-freshness.ts` (Decision D31). Before launching Verify, AIES inspects the mtimes of all runtime-loaded files against process start time. If any are newer, Verify fails fast in 3 ms with `stale_runtime`, instructing the user to relaunch AIES.

### EZE-493: Self-Hosting Test Harness and Nested Sandbox Isolation
- **Problem**: Running `npm test` or `npm run check:isolation` inside Verify's read-only sandbox yielded 54 failures:
  1. Tests attempting to create nested sandbox sockets failed with `listen EPERM` on `/tmp/claude/srt-mux-*.sock`.
  2. Tests executing launcher bootstrap attempted to write to `~/.local/share/aies/agent/settings.json` or acquired locks on ambient `auth.json.lock`.
- **Fix**: Implemented in Session 8 on branch `fix/eze-493-self-hosting-main`:
  - `scripts/test-harness.sh` isolates `AIES_HOME` and `PI_CODING_AGENT_DIR` into temporary directories per run.
  - `tests/helpers/nested-sandbox.mjs` detects when running inside an existing outer sandbox and explicitly skips OS socket enforcement tests (19 skips) while allowing standard logic to run.
  - Full suite achieved 1,121 pass, 19 explicit skips, 0 failures inside Verify.

## 4. Self-Hosting Verify

The central architectural hurdle discovered during this sprint was **Self-Hosting Verify**.

In consumer projects, Verify executes in a contained, read-only sandbox. It runs `npm test` or build tools against application code, which naturally operates within that sandbox. However, when AIES is used to develop AIES:
- AIES's own test suite tests whether the launcher boots cleanly, whether symlinks are created, whether settings are seeded, and whether sandbox tools restrict execution.
- When AIES's test suite ran inside Verify's sandbox:
  1. The launcher tried to write to the ambient user profile (`~/.local/share/aies`), triggering write denials or contention on `auth.json.lock`.
  2. The sandbox tests tried to spawn an inner `sandbox-runtime` daemon, creating a Unix domain socket inside `/tmp/claude/`. The outer sandbox denied `bind`/`listen`, producing `listen EPERM`.
  3. Individual tests created mock persistent profiles under `homedir()/.aies-test`, escaping the test runner's scratch space.

This created a false impasse: Verify could not PASS AIES changes because AIES's own tests could not run inside Verify.

The solution in EZE-493 was not to loosen Verify's permissions (which would compromise isolation), but to make the test harness aware of isolation:
- `scripts/test-harness.sh` ensures every test run uses a strictly isolated, ephemeral `AIES_HOME`.
- `tests/helpers/nested-sandbox.mjs` queries the environment. If already restricted by an outer sandbox, it explicitly marks the nested socket tests as `SKIP` with a clear explanation, rather than failing.
- Real behavioral tests and regressions still execute and fail on error.

## 5. Repo and Worktree Guard

In Session 4 (EZE-489), dogfooding caught a severe safety breach: an agent running from `~/Proyectos/Developer/Mi-Porfolio` loaded an issue belonging to the `AIES` project, and the Parent LLM began issuing edits and bash commands against the AIES repository.

To enforce workspace boundaries, Decision D30 implemented `repo-guard.ts`:
- **Identity Check**: Compares ticket `project` with the current workspace directory and git root.
- **Granular Policy**:
  - Read-only queries (`git status`, `aies_ticket show`, source inspection) remain permitted regardless of cwd.
  - Destructive tools (`edit`, `write`, mutating `bash`, `aies_delegate worker`) are blocked before execution if repo identity does not match.
- **Escape Hatch**: An explicit environment variable `AIES_ALLOW_REPO_MISMATCH=1` allows override when cross-repo orchestration is intentionally required.

## 6. Stale Runtime and Process Lifecycle

One of the subtlest bugs surfaced in Session 1 and solved in Sessions 5–7 was the **stale runtime** problem.

Because Pi runs extensions in Node.js via `jiti` and spawns subagents in-process:
1. When AIES starts, `extensions/aies-agents/*.ts` are loaded into memory.
2. A Worker modifies `extensions/aies-agents/verify.ts` on disk to fix a bug.
3. Parent delegates to Verify.
4. Verify runs inside the existing Node.js process, executing the **old, in-memory code**, not the modified file on disk!

In Session 1, this led to confusing forensic sessions where the model believed the code was fixed, but the child agent continued executing the previous logic.

Decision D31 resolved this with zero magic:
- No hot reloading, no `eval`, no file watchers, no complex cache invalidation.
- The `runtime-freshness` module checks file `mtime` against process start time. If any runtime-loaded file was modified, Verify refuses to launch, immediately returning `stale_runtime`.
- The user is instructed to restart AIES (`aies`), ensuring every verification executes against fresh, clean in-memory state.

## 7. Completion and Linear Workflow Flaw (EZE-503)

A critical workflow finding surfaced across sessions (notably Session 5 and Session 8) regarding ticket completion:
1. Worker implements a fix.
2. Verify returns `PASS`.
3. Parent immediately invokes `aies_ticket complete` and triggers `mcp save_issue` with `state: "Done"`.
4. The session terminates while an explicit final action requested by the user—such as human review or a subsequent git commit—remained pending.

**The Finding**: A `Verify PASS` verdict is an evaluation of work unit criteria, **not** an automatic completion signal. It does **not** imply `Done` when an explicit final action requested by the user remains pending (e.g., explicit user instructions: *"no commit todavía"*, *"detente para revisión"*, or awaiting human verification).

Treating `Verify PASS` as an unconditional trigger to close the ticket in Linear caused ticket state to drift ahead of reality, marking work as completed before the developer had reviewed the diff or committed the code.

## 10. Excessive Delegation and Duplicated Work

The session traces revealed substantial inefficiencies in multi-agent coordination:
1. **Delegation Churn**:
   - Session 4 required **10 delegations** (1 Explore, 5 Workers, 4 Verifications) to deliver a 3-file change.
   - The Parent accepted a PASS from Verify 1, then reopened the implementation to tweak path lookups, triggering two subsequent Verify failures (uniqueness error and missing doc entry D30) before achieving a final PASS on revision 4.
2. **Context Amnesia**:
   - Each child agent started with a blank slate.
   - Workers and Explorers spent dozens of tool calls running `find`, `rg`, and reading `package.json` to re-discover facts that had already been established three minutes prior in a sibling delegation.
3. **Forensic Archaeology by Parent**:
   - In Session 1, Parent executed 38 bash commands grepping through session JSONL files on disk to deduce why Verify failed with `invalid_completion`.
   - In Session 3, Parent executed 19 bash commands searching for MCP auth tokens and reading JSONL logs.

## 11. Evidence for Work Unit Memory

The inefficiencies above provide undeniable empirical evidence for **Work Unit Memory**:
- **What is Work Unit Memory?** A persistent, structured blackboard associated with the active Linear ticket and repository, maintained across the lifetime of the work unit.
- **Why is it needed?**
  1. **Eliminate Redundant Discovery**: Once an Explore child maps the architecture (e.g., locating the 66 extension modules, identifying the ticket transport, or identifying the test runner), those facts should be recorded in memory. Subsequent Workers and Verifiers should consume them directly instead of re-exploring.
  2. **Track Mutation History**: When a Worker modifies files, the changed paths, diff summary, and intent must be recorded so Verify immediately knows what to test without re-running `git status` or guessing changed scope.
  3. **Persist Repair Context**: When Verify fails (as in Session 4 with the uniqueness defect), the failure signature and exact failed assertion should be passed directly into the repair Worker's memory rather than requiring Parent to hand-craft a massive prompt.
  4. **Enforce State Gates**: Work Unit Memory can gate ticket completion on explicit developer actions.

## 12. Possible Role of Jev

Investigation of `pi-mcp-adapter` identified `jev-client.ts` and `jev-contracts.ts` (a structured evaluation engine providing `choice`, `score`, and `noul` probabilistic judgments over state without spawning full conversational LLM sessions).

**Crucial Boundary**: Jev is **NOT** a substitute or replacement for Verify. Verify remains the authoritative, independent validator of code, test execution, and acceptance criteria in the working tree.

**Potential Role of Jev in AIES**:
1. **Work Unit Memory Gates**: Acting as the decision gate for writing to, retrieving from, or evicting items in Work Unit Memory (evaluating whether a piece of context is stale, duplicate, or relevant).
2. **Routing & Explore Decisions**: Determining whether an Explore delegation is strictly necessary based on existing memory, or whether context is already sufficient to delegate directly to Worker.
3. **Relevance and Prioritization**: Scoring and prioritizing search results or session history before passing them into agent prompts.
4. **Repetition Detection**: Identifying when a Worker or Parent is caught in a repetitive inspection or repair loop.
5. **Pre-flight & Escalation**: Running fast semantic pre-flight checks before expensive multi-agent pipelines are launched, or deciding when to escalate an ambiguous state to the user.

## 14. Learnings Belonging to v1.1

Architectural improvements deferred to v1.1:
1. **Work Unit Memory Implementation**: Design and implement the shared memory store across delegations to eliminate context loss, reduce agent tokens, and avoid repetitive whole-repo scans.
2. **Jev Integration**: Integrate Jev for memory governance (write/retrieve/evict gates), routing decisions (e.g. skipping redundant Explore), repetition detection, and pre-flight checks—preserving Verify as the code validation engine.
3. **Subagent Context Compaction**: Automatically compact child session traces before returning results to Parent to reduce Parent token accumulation.

## Cross-session findings

### 1. Wasted Time
- **Forensic Archaeology**: Parent agents spent 15–30 minutes per session running repetitive bash commands (`sed`, `grep`, `node -e`) inspecting JSONL session logs on disk to diagnose child errors.
- **Slow Verification Children**: Verify delegations routinely ran between 12 and 33 minutes, even when validating small 2-file changes.
- **Ping-Pong Iterations**: Redundant implementation-verification loops (e.g., Session 4 taking 128 minutes across 10 delegations) dominated total development duration.

### 2. Context and Token Waste
- **Massive Child Footprint**: Out of 117M tokens, over 106M tokens (90.8%) were consumed by child agents.
- **Repeated Tool Schema and Prompts**: Spawning fresh subagents without shared state forced the injection of full system prompts, tool definitions, and repo context on every delegation.

### 3. Re-reading and Re-investigation
- **Amnesia Across Delegations**: Each Worker and Verify child re-ran filesystem exploration (`find`, `grep`, `ls`, reading `package.json` and `ARCHITECTURE.md`), rediscovering known facts that had already been established in prior steps of the same ticket.

### 4. Unnecessary Routing
- **Parent Doing Worker Tasks**: In several runs (Sessions 1, 3, and 4), Parent performed direct bash inspections, file reading, and test execution instead of delegating immediately or trusting child results.

### 5. Verify
- **Rigid Matching**: Text equality matching in Verify proved fragile in production, necessitating the structural index contract (EZE-488).
- **Self-Hosting Isolation**: Verify cannot verify harness repositories without an isolated test harness (EZE-493).
- **Stale Code Execution**: In-process child execution requires an explicit stale runtime guard (EZE-492) to prevent validating in-memory ghosts.

### 6. Linear and Workflow
- **Payload Loss**: Manual LLM proxying between MCP and tool arguments dropped critical ticket sections (EZE-490). Direct event capture is mandatory for large payloads.
- **Premature Done State (EZE-503)**: Verify PASS does not imply Done when an explicit final action requested by the user (such as review or commit) remains pending. In Sessions 5 and 8, tickets were marked Done in Linear despite uncommitted changes and explicit user instructions ("no commit todavía").

### 7. Isolation
- **Profile Contention**: Tests accessing ambient `~/.local/share/aies` or `~/.pi/agent` caused intermittent lock failures (`auth.json.lock`).
- **Nested Sandboxing**: Sandboxed runners cannot spawn child sandbox runtimes without socket collision detection.

### 8. Models
- **Model Heterogeneity**: The Parent model does not dictate child models. Session 8 demonstrated a heterogeneous stack (Parent: GPT-6 Luna; Explore: GLM-5.3 Flash; Worker: MiMo-v2.6 Flash; Verify: GPT-6 Luna).
- **Context and Telemetry Limits**: The sessions involved diverse task complexities, and `costAgents` was null for several sessions. Cost and efficiency cannot be ranked authoritatively; observations reflect specific task dynamics rather than generalized model benchmarks.
- **Observed Behaviors**: Qwen3.8 Flash exhibited high token consumption in child delegations (56M); DeepSeek v4.1 Flash was deployed across 6 sessions with tight adherence to structural schemas; GPT-6 Luna / Codex demonstrated strong script generation capability in Session 8 with concise parent token usage.

### 9. UX and Observability
- **Provider Misattribution**: The right rail and agent card initially misattributed provider names during active child delegations (fixed in EZE-487).
- **Elapsed Time Tracking**: Run elapsed timers were resetting across child stages (fixed in EZE-469).
